# Pipeline Task Decomposition

## Summary
A full-stack CNC laser-cutting quoting and ordering application. Authenticated customers upload a DXF drawing, the backend parses its geometry (entity extraction, `$INSUNITS` unit normalization to inches, total cut length, bounding box), lets the customer pick a material and add bend lines, then grid-nests the part onto sheets and prices an immutable quote (`max(minimum_order, setup_fee + cut_length_ft × cost_per_linear_foot + sheet_cost + handling_fee + bends × cost_per_bend)`, integer cents). The customer reviews an itemized cost breakdown and an animated canvas work-bed visualization of the nested sheet with a simulated laser cut, chooses a shipping method, and pays through Stripe Checkout; a signature-verified, idempotent webhook creates the order and a confirmation email is sent. Admins manage materials, shipping methods, pricing/machine/upload/business/payment settings, orders, and backing-service credentials.

**Stack reality check (binding for all agents):** the scaffolder produced the *enterprise* stack — **Angular 19 frontend + NestJS backend + Prisma/PostgreSQL + tRPC glue** (`colossus.stack.json`), with `Role { USER, MANAGER, ADMIN }` and `ColossusAccount` already in `backend/prisma/schema.prisma`. The spec text describes FastAPI/SQLAlchemy/React/Vite. **The spec's behaviour, routes, entities, formulas and scenarios are authoritative; its Python/React file paths are not.** Every task below is expressed in the scaffolded stack. Do not create `backend/app/**` Python modules or a Vite/React `frontend/src/pages` tree. See Open questions for the DXF-library consequence.

## Surface contract

### Entities (Prisma models)
`User` (existing — extend), `ColossusAccount` (existing — do not change shape), `RefreshToken`, `Material`, `ShippingMethod`, `Drawing`, `BendLine`, `Quote`, `Order`, `WebhookEvent`, `SystemSetting`.

### Backend API
tRPC routers under `/api/trpc` (typed glue, per `colossus.stack.json.glue.api_client = "trpc"`), plus three REST controllers where tRPC cannot serve the shape (multipart upload, raw-body webhook, receipt document).

| Health | `GET /api/health`, `GET /api/health/deep` | public |
| Drawings | `POST /api/drawings` (REST, multipart), `drawings.byId` | authed, owner-scoped |

### Frontend routes (Angular `app.routes.ts`, hash-routed SPA)
`/login`, `/signup`, `/quote/new/upload`, `/quote/new/material`, `/quote/new/bends`, `/quote/new/review`, `/quotes?page=&sort=`, `/quotes/:id?panel=breakdown|nesting&modal=confirm-order`, `/checkout/:quoteId/review`, `/checkout/:quoteId/shipping`, `/order/confirmation/:orderId`, `/orders?page=&status=`, `/account`, `/admin/settings`, `/admin/materials?modal=edit-material&id=`, `/admin/pricing`, `/admin/machine`, `/admin/orders`, `/admin/business/branding|contact|payment|shipping`.

`/login`, `/signup` and the health endpoints are public. Everything else is behind `authGuard`; `/admin/**` is additionally behind `adminGuard` (role `ADMIN`).

### Auth model — `full_auth`
Signup is open. The first registered user becomes `ADMIN`; every subsequent signup becomes `USER` (the spec's "customer"). `MANAGER` stays in the enum for the platform contract but is not assigned by app flows. Admin nav and `/admin/**` are gated by a role check.

## Open questions
- **Stack conflict (highest priority).** The spec prescribes FastAPI + SQLAlchemy + React/Vite; the scaffolded repo is NestJS + Prisma + tRPC + Angular 19 with a certified stack contract. These tasks target the scaffolded stack. If the intent was genuinely a Python backend, the pipeline must be re-scaffolded before any of the backend tasks run.
- **`ezdxf` has no JavaScript equivalent.** The spec's parser design (`ezdxf.path.make_path`, `path.flattening`, `ezdxf.bbox.extents`) is Python-only. In the Node backend this must be re-implemented over an npm DXF reader (e.g. `dxf-parser`) plus hand-written arc/circle/bulge flattening. Bulge-to-arc conversion and spline handling are the risk areas; splines are out of the spec's supported entity list, so they are currently ignored — confirm that is acceptable.
- **Fernet → AES-256-GCM.** The spec names Fernet (Python `cryptography`). The Node equivalent used here is AES-256-GCM keyed from `APP_SECRET`; the key-rotation failure mode and env-fallback behaviour are preserved. Confirm the substitution.
- **Integration env keys are synthetic.** `POSTGRESQL_API_KEY`, `REDIS_API_KEY`, `MINIO_VIA_BOTO3_S3_API_API_KEY` and `EZDXF_API_KEY` are pipeline-derived names, but PostgreSQL/Redis/MinIO are addressed by connection URL/credentials, and `ezdxf` is an in-process library with no credential at all. These tasks resolve the derived keys for admin-settings parity while the real clients use `DATABASE_URL` / `REDIS_URL` / MinIO endpoint+access-key+secret-key. Confirm whether `ezdxf` should appear in the settings UI at all.
- **Role naming.** The spec calls the non-admin role `customer`; the stack contract fixes `Role { USER, MANAGER, ADMIN }`. These tasks map customer → `USER` and leave `MANAGER` unassigned by app flows. Confirm no `MANAGER`-specific behaviour is expected.
- **Platform-seeded admin vs. first-signup-becomes-admin.** `ColossusAccount` seeding already mints an ADMIN login, which closes the spec's "first signup on a public URL becomes admin" risk — but it also means the first *signup* will not be the first *user*. Confirm the intended precedence (these tasks keep spec behaviour: first row in an empty `User` table wins, which the seed will normally already occupy).
- **Receipt format.** The spec says "PDF/HTML" for `GET /api/orders/:id/receipt`. These tasks assume HTML (no PDF toolchain in the scaffolded stack). Confirm.
- **Unspecified values.** The spec does not fix default `pricing` values (setup fee, cost per linear foot, cost per bend, handling fee, minimum order), `machine` bed dimensions, part spacing/margin defaults, `upload.max_upload_bytes`, `quantity_min/max`, order/confirmation number formats, or the quote-expiry policy. db_agent picks sensible seed defaults; these are admin-editable and should be reviewed.
